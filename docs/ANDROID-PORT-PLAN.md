- SDK 安装了 build tools 36.0.0；AGP 8.9.0 实际另安装并使用默认 35.0.0。保留上游 AGP 的 SDK 36 支持提示作为已知警告，不为提示单独升级工具链。

- 包名 `io.github.pvzonline.android`，名称 `PvZ Online Dev`，最低 API 24，当前开发签名。资源管理快捷入口同步改到新包名，Java namespace 保持底座命名。
- 本机 ADB 可用，检查时没有连接设备。用户选择 MuMu、Android 12、9 GB 内存，模拟器稍后由用户启动；不自动启动或调整模拟器配置。

### P0 尚需一个运行验收节点

MuMu 启动后，先检查 ADB 地址与 `ro.product.cpu.abilist`，再安装底座包。ARM64 包可否安装取决于该实例的 ABI/翻译支持，不能只凭 Android 12 判断。

一次验收覆盖：安装 → 启动资源导入 → 导入本机正版资源 → 主菜单 → 进入一关 → 种植/拾取阳光 → 音频 → 退出。只检查这条路径，失败时保存简短 logcat 与一张截图定位。

若 MuMu 不支持 ARM64 包，则额外构建 x86_64 开发 APK，而 ARM64 仍是手机交付目标；不要为适配模拟器把最终手机架构改成 x86_64。模拟器通过只能证明功能路径，不能证明真实 ARM 手机帧率、触控舒适度、耗电或温控；9 GB 内存也不能替代这些证据。

### 根据源码对照补充的迁移任务

1. **先做接口适配表，再搬玩法。** Portable 的 `Sexy.TodLib` 已改为 `PvzpLib`，字体抽象为 `_Font`，文本接口使用 `std::string_view` 与 `char32_t`，成就页面为 `AchievementsScreen`。按真实 API 适配，不能全局机械替换名称。
2. **显式加入新目录编译。** Portable 的 CMake 源文件列表不包含 `src/Lawn/Run` 或 `src/Lawn/Online`；添加功能时同批登记源文件，避免“文件存在但没有进 APK”。
3. **先确认枚举，再做传怪。** Portable 尚无本项目新增的带防具植物头等枚举；核对 SeedType/ZombieType 值和计数，以及按计数分配的资源/定义表。必要时用协议编号到本地类型的显式映射，不能靠当前排列碰巧一致。
4. **复用现有 Unicode 能力。** Portable 已有 UTF-8 解码与 `char32_t` 字符查找。首先确认合法中文资源的字体覆盖与 mod 新文案字符集合，优先复用；仅在缺字时补字体来源与绘制方案，不照搬正在修改的 Windows GDI 实现。
5. **复用已有输入基础。** 底座已经处理 SDL_TEXTINPUT、软键盘输入矩形、前后台事件；房间码/名称对话框接入这些能力，不重新实现整套 Android 输入桥。
6. **后台策略分成两类。** 主菜单/单机使用底座既有最小化与焦点处理；联机另做真实时间、席位保留和一次性事件一致性处理。现有观战快照不充当重连恢复凭据。

### 调整后的近期实施顺序

- **下一交付：MuMu 底座运行记录 + P1 适配表。** 模拟器未启动期间可以继续只读梳理；运行验证未通过前不批量覆盖战斗文件。
- **再交付：单机两关闯关闭环。** 首先迁 Run 数据与最小 UI/Board 挂点，增益先接代表性路径，随后补完整表；保留所有遗漏项清单，不把占位效果写成完成。
- **随后：最小 PC/Android 联机闭环。** 协议与跨平台传输层先到位，验证建房、名册、同关启动、一次漏怪和一次队伍结算，再迁移观战等高载荷功能。
- 各阶段保持现有 Windows 来源和 MOD_BUILD 的兼容记录；开始 P1 时重新检查来源提交，若要升级来源，只挑已提交且必要的改动，避免不断追着 Windows HEAD 重做移植。

### 效率与交付补充

- 构建入口固定为 `build-android.ps1`，可单独执行 Dependencies/Native/Apk，源码和二进制缓存复用。
- 后续修改玩法时只编 Native + Apk；修改 Java/UI 资源时只打 Apk，不重装 SDK、不重建第三方库。
- 当前原生库未剥离副本保留在 build 目录，Gradle 打包时剥离符号。发布时另保管对应符号与构建身份，不把巨大的原生调试文件装进 APK。
- 当前只有开发签名，最终发布身份、持续增加的 versionCode 和签名备份必须在面向玩家发布前明确。
- 准备阶段不需要写玩家玩法更新日志；从玩法迁入开始维护 Android 独立更新记录，并标明 PC 兼容范围，避免误改 Windows 当前批次日志。
- 现有 Android 工程无 Git 历史。第一次功能修改前建立本地版本管理基线，并保留上述真实上游来源说明；不伪造上游提交。

## 目标与默认假设

以 wszqkzqk/PvZ-Portable 为底座，把现有 PvZ Online 合作玩法迁入，生成可安装、可更新的 ARM64 Android APK，并支持与当前 Windows 客户端联机。

以下是规划默认值，不代表用户已确认全部产品细节：首版横屏、保留 800×600 逻辑画布与等比缩放；优先 arm64-v8a；沿用现有中继；保留闯关、无尽与六席位规则；不新增 PVP。Android 最低版本暂沿用底座的 API 24，待目标手机确认。

首版交付分为“可运行底座”“最小联机 APK”“完整玩法 APK”。不把 APK 编译成功当作完整移植成功。

## 已核对的事实与未知项

- 现有客户端 Windows x86，网络层使用 Winsock、Windows 线程、临界区和 Interlocked；中文 mod 文本使用 GDI。两者不能直接用于 Android。
- 现有闯关检查点已有固定宽度显式序列化；仍需核对枚举、版本和所有扩展字段。
- 当前协议头 MOD_BUILD 为 42；迁移基线必须在开始时重新取 Git 提交和实际版本，不能永远固定为此值。
- 原工程工作区正在变化，涉及汉化与字体代码。移植只取明确的已提交基线，不拷入未知完成状态的本地修改。
- Portable 已提供 Android 工程、SDL2/GLES 后端及资源导入。其 Gradle 配置为 compile/target SDK 36、min SDK 24、默认 arm64-v8a、AGP 8.9.0。
- 本次 PATH 检查未找到 java/adb；这只说明未在 PATH 中发现，不证明机器没有 SDK/JDK。第一阶段继续定位安装目录。
- 观战快照存在，但不能据此推断具备断线后完整棋盘恢复。当前重连部分以帧计时，Android 后台暂停后必须处理真实经过时间。
- 尚未完成两套代码差异地图，暂不承诺工期、零服务器修改或完整存档互通。

## 工程组织与兼容策略

1. 在本目录下建立独立 `pvz-online-android/` 工程，保留现有 Windows 工程和运行目录。固定 Portable 的提交，记录本项目的来源提交。
2. 先识别两套工程相同的类、接口与语义；不能仅凭文件名相同就整文件替换，不能默认 Git 合并能够完成迁移。
3. 把纯玩法模块优先移入；平台相关代码保持小接口。网络传输沿用 NetLink 对外 API，Android 实现采用 POSIX socket + 标准线程/同步设施，核对关闭、发送超时、错误码与线程退出语义。
4. 初期维持手机独立工程，建立迁移清单：来源提交、功能、目标文件、状态、PC 兼容影响。待移植稳定后决定是否形成长期共用核心，避免第一阶段大规模重构。
5. 不因“平台不同”自动抬 MOD_BUILD；若消息格式、实体编号或两端计算规则变化，则同步评估 Windows 更新和版本兼容。兼容检查既看编号也看行为。

## 执行阶段与完成标准

### P0：固定基线、跑通构建

- 定位 JDK、SDK、NDK、CMake、Gradle wrapper 和 SDL/音频/图像依赖来源，按固定底座要求记录精确版本。
- 首选本机可重复构建；本机受阻时评估项目现有 CI，不为取得 APK 临时改写整套构建体系。远端构建不上传正版资源或签名秘密。
- 原样构建 Portable，使用本机正版资源验证启动、进入一关、音频和退出。
- 确定独立包名、应用名、存档目录。开发包与最终发布签名分开，长期保管发布密钥；正式更新不能随意换签名。
- 产物：原样基线 APK、构建说明、版本锁定记录。若底座本身不能在目标设备运行，先解决这一阻塞，再迁玩法。

### P1：差异地图与最小玩法迁入

- 以相对上游的实际功能改动为单位梳理：主菜单/选卡、Board 挂点、Plant/Zombie/Projectile、RunState/RunBuffs/RunZombieRoster、协议/会话、ModText。
- 特别列出新增实体字段、枚举值、动画/碰撞逻辑、暂停和奖励流程；保留 Portable 的跨平台容器、指针修复和保存实现。
- 先迁入一条单机闯关流程：开局设置 → 选卡 → 对局 → 奖励 → 下一关。优先编译排错，必要时暂用文本按钮验证流程。
- 完成标准：能完成两关并退出重进检查点；只要求覆盖这一闭环，不逐条验所有 buff。

### P2：最小手机/PC 联机

- 迁入协议和 NetSession，实现跨平台 NetLink；为 Android 添加 INTERNET 权限，核对最终合并的 Manifest。
- 房间码、玩家名接入软键盘；能建房、加入、显示名册并启动。
- 保持现有中继路由。先使用开发中继或独立测试房间，不升级现有公网服务来试错。
- 核对自然出怪规则、漏怪载荷、血量/防具/类型编号、末席判败、全席判胜、暂停、退关和选卡等待。
- 完成标准：手机与 Windows 完成一局，实际触发一次漏怪传递和一次队伍结算。失败按触发点排查，不重复全量回归。

### P3：完整玩法和触屏

- 迁入完整植物增益、新增僵尸、巨型 Boss、无尽难度曲线、赠送阳光、聊天、观战和检查点续档。
- 保留 4:3 棋盘，可在侧边空余区域放辅助按钮；不同宽高比及安全区域使用同一坐标转换，避免画面与命中区域错位。
- 为聊天、观战、赠送阳光、暂停提供触屏入口。观战优先考虑点击切换/再次点击返回，避免强制长按遮挡；赠送阳光直接选队友。
- 处理铲子/取消选卡、拖动与抬手、误触、Android 返回手势、软键盘遮挡和名字输入长度。不默认必须实现双指同时操作。
- 汉化复用 Portable 可用的 UTF-8/字体路线，检查当前 mod 中文字库来源、字号、裁剪和换行。不能照搬 GDI 修补代码。
- 完成标准：主要玩法无需外接键盘；检查代表性的三类增益、一个新增僵尸、Boss、赠送阳光和观战即可，异常再扩大范围。

### P4：生命周期、资源、性能与发布

- 先明确前后台策略。建议首版切后台视为暂离，按真实时间判断重连/席位保留，返回前台提示恢复或退出；不要承诺被系统杀死后无损续战。
- 单独分析后台期间漏怪与一次性事件丢失：若没有重放/确认机制，不能仅凭重新连上就继续一个已不一致的对局。选择安全终止或增加最小恢复机制，重大语义变化先与用户确认。
- 资源使用底座的 SAF 导入；适配 Steam 资源与中文覆盖包，资源目录、缓存、存档分离，处理取消导入/缺失资源的明确提示。
- 为新 buff 字段接入 Portable 的序列化机制。先支持手机端自洽存档；PC 检查点/局内存档互通分别评估，不混为一个承诺。ARM64 不复用原生结构布局缓存。
- Release 包保留本机符号文件和可导出的诊断日志；核对依赖架构、当前 Android 原生库页大小兼容及安装目标，分发 APK 不含 PopCap 原版素材。
- 用目标手机观察高怪量/多弹体场景。优先减少重复工作和观战绘制成本，不擅自削弱玩法或改为按设备各算不同难度。
- 完成标准：Release APK 能安装、更新保留存档、导入资源；一次前后台切换与一次网络中断得到明确结果；记录设备和剩余限制。

## 验证预算与编写效率

- 编译是每个阶段的基本检查；无新风险不反复清理重建。
- 每阶段一条关键路径冒烟；纯文案与局部布局不写镜像实现的测试。
- 复用已有协议黄金向量；协议编解码/跨架构存档变化才运行对应专项检查。
- 全屏 Windows 截图规范不机械套用手机；Android 用实际画面和触摸坐标验证。只有出现渲染/命中错误才增加像素测量和短期插桩。
- 不预先建立大型测试框架，不穷举全部 buff、全部手机、全部六人组合。两人通过后补一次多席位名册/路由检查；没有多台设备时如实记录未验范围。
- 每阶段结束整理一次问题，不为了单个编译错误打断用户；产品规则、兼容破坏、外部服务变更和显著范围增加及时询问。

## 需要在实施节点确认的细节

开始前：主仓库选择、目标手机型号/Android 版本、是否必须首版与 PC 互通。未收到补充时规划仍用本文默认值，不把缺少设备实测写成已验。

构建可运行后：应用名称/包名、首版辅助按钮方案。没有强偏好可先使用可修改的开发配置。

生命周期实现前：切后台是否允许全队暂停、最大容忍时长、被杀进程是否要求恢复。涉及队伍规则，不能凭等待时间代替确认。

发布前：仅自用/小范围测试或公开分发、长期签名保管位置、源码与许可证交付。完整许可归属按实际文件核对，不把现项目 CC0 描述直接套给 Portable。

## 当前推荐的第一步

执行 P0，同时形成 P1 差异地图。拿到能启动的底座 APK 后再批量迁入玩法。每次进度报告说明“已完成、目前阻塞、下一交付物”，不提前宣称整个手机移植完成。
