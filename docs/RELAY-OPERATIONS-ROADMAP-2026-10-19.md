## 目标与现状

玩家继续只使用“创建房间、公开大厅、房间码”，不出现选服页面或服务器地址。负载分配和维护由程序处理，管理员能在统一网页看出瓶颈、维护进度与失败原因。

当前源码已经实现两节点探测、按房间和连接占用自动建房、双服大厅聚合、完整房间码定位。实际选择逻辑位于 `Lawn/Online/AutomaticRooms.h`；内置节点目录与查询位于 `RelayNodes.h`。本计划不重复建设这些功能。

目前缺少的能力：

- 选择未参考出口流量、拥堵和维护状态；接近相同负载时缺少随机分散，瞬时建房可能集中到同一节点。
- 探测等待全部结束后才选择，坏节点可能拖慢好节点；建房遭遇瞬时满额后没有完整的安全自动重试流程。
- 节点目录写在客户端中，新增节点需要更新客户端。
- `server/relay/main.go` 没有维护排空、配置重载和优雅退出；房间及重连保留位在进程内存中，直接重启会丢失。
- 服务有本机状态页、累计计数和基础速率，但没有固定采样趋势、统一两服视图或发布流程。
- 当前源码保护上限为每节点 256 房间、512 连接、每房 6 人。这是保护额度，不是满负载运行承诺；连接还包含查询等非玩家连接。

公网信息沿用此前部署记录，不当作本轮实时巡检结果：节点 2 已部署 `2026-10-19-multinode1`；节点 1 的实际版本与 256 房扩容仍需上线前重新核实。原服公网带宽确认为 3 Mbps，新服带宽需核实，不能直接承诺总稳定人数。

| P1 | 带宽感知自动分配、安全重试、容量预留 | 创建更可靠，尽量绕开繁忙或不可用节点 | P0 提供兼容的新查询能力 |

P0、P1 的客户端和服务器配套工作应作为第一批可验收的能力一起交付；P2 在隔离环境完成整套演练后再进入公网维护流程。

## P0：先把负载与维护基础做准

1. 每 5 秒固定采样一次，用固定长度环形缓冲保存最近 10 分钟；页面打开数量不增加采样任务。记录应用发送、连接、房间、队列、写失败、超时、进程 CPU、主机内存压力。
2. 显示最近 1 分钟错误增量，累计计数单独保留。明确进程 CPU 的单核百分比与整机百分比，防止两核机器的数值被误读。
3. 配置中显式填写公网带宽，并单独设应用发送预算。应用计数不包含 TCP/IP 开销、重传及其他服务，不能把“3 Mbps 减去应用流量”标为精确剩余容量。上线前用云监控或系统出口统计校准预算。
4. 增加正常、停止新建房、更新中、观察中、故障等状态。存活检查与“是否接收新房间”分开；正常转发旧房间但不收新房属于可预期维护状态。
5. 支持本机管理命令读取状态、停止新建房、恢复接收、重载配置。热调范围先限于带宽预算、权重、软阈值等；降低软阈值不踢出现有玩家。首版不把固定连接池硬上限改成任意热调参数。
6. 配置先完整校验，再一次性生效；错误配置保留旧值。管理操作沿用 SSH 和本机接口，不把控制权限开放到公网状态查询。

新公开查询只提供客户端分流所需的能力、可接收状态、负载与采样新鲜度，不公开管理凭据或详细主机信息。保留旧容量查询的原有格式，扩展通过新版本或新能力协商，不向旧游戏连接强发未知消息。

验收：固定内存占用；无页面访问时趋势仍连续；配置错误不改变运行配置；重载期间房间持续通信；旧容量查询、旧大厅和原有加入协议继续通过。

## P1：带宽感知负载均衡

分配单位是“新房间”。一个房间的成员、关间补位及重连始终连接同一节点。玩家流量直连所属节点，不经过某一台 3 Mbps 服务器集中转发。

- 先排除不可用、停止新建房、信息过期或已超过软额度的节点。
- 房间、连接、应用发送预算等按占用比例判断，最紧张的一项主导；队列持续增长、近一分钟写失败等作为拥堵保护信号。CPU、主机内存压力参与保护，具体阈值由基线与压测确定。
- 在负载接近的可用节点间按容量加权随机，减少大量玩家同时选择同一台的情况；延迟过高可降低优先级，不能为了几毫秒牺牲明显更多容量。
- 健康节点已响应时，只给其他探测一个短暂补充窗口，不固定等坏节点耗尽全部超时。缓存具有期限；所有回退共用整体时限，返回/取消立即终止后续动作。
- 服务端原子核验是否允许建房，客户端分数只用于建议。需要明确的“繁忙/维护，可尝试其他节点”结果，不能突破房间和连接保护。
- 自动重试只用于尚未建立房间的创建流程，限制次数。服务器明确拒绝可尝试下一节点；已创建或响应丢失的模糊结果，需要请求标识和去重/确认机制，避免在两服留下重复房间。确认建房后固定节点。
- 输入完整房间码或点击大厅条目时只访问目标节点；不能因为目标繁忙改进另一服同码房。
- 给查询、握手和已有房间重连保留受限的处理余量。当前 512 额度在解析请求前统一限制，需要重新划分有界配额；不能增加无限匿名连接，也不能承诺物理上已满时仍必然接入。
- 旧节点没有新指标时使用保守降级，状态显示“指标不完整”；不把未知负载当成零。

验收：模拟一服满额、出口限速、慢响应、维护、离线，以及两服同码、同时建房、取消和响应丢失；新建房合理分散，无重复房、串房或超额。满额与拥堵测试在隔离节点进行，不对真实玩家服务器灌入压测连接。

## P2：配置热更新与程序滚动更新

区分两种更新：配置可在原进程中即时重载；程序版本先实现“停止新建房，等待房间自然结束，再逐台更新”。现有对局不被强制切换服务器。

建议发布流程：

1. 上传到独立版本目录，核对可信来源、散列、运行架构、配置及端口；不覆盖正在运行的程序。
2. 检查另一节点的负载余量，确认它能继续接收新房；余量不足时保留旧服务并等待。
3. 本服进入停止新建房状态，由服务器拒绝所有新建请求，包含旧客户端。统一大厅继续列出符合公开条件的已有房间；原房间成员加入、关间补位及重连继续允许。
4. 等待房间、重连保留位以及已受理但尚未结束的建房握手清空；维护开关与建房检查需原子化，防止检查之后又创建一间房。排空期间不能直接关闭全部 TCP 监听，否则会破坏已有房间的重连和加入。
5. 达到空房条件后退出旧进程、切换版本并启动；妥善退出后台循环，关闭监听后的 Accept 错误应终止循环，避免空转刷日志。
6. 新进程先保持不收公众新房，通过存活、管理、查询与专用小房间自检，再逐步恢复接收。状态页展示实际运行的版本、阶段、剩余房间与等待时间。
7. 第一个节点稳定后再处理第二个。维护过程保留小型本地状态记录，任务中断后可继续判断实际阶段，避免误把重复执行当成全新安装。

需要说明的边界：

- 当前线上旧程序尚无排空功能，第一次安装这些能力仍需逐台安排维护，无法由外部替换程序让原内存房间自动继承。
- 无尽房间可能长期不结束；默认等待超时只提示管理员，不自动终止房间。管理员可取消维护或另选窗口。不能将“等空房”承诺为定时必能完成的热更。
- 两台都高负载时，维护会减少可接新房容量；要缩短等待需留维护余量、临时加第三服或提升容量。增加第三服也不会自动迁走原房间。
- 失败回退先保持停止新建房状态。如果新版本还未承载真实房间，可以回到旧版本；如果已有真实房间，应先保护并排空，不能为回退再次打断玩家。
- 进程崩溃、机器重启和跨机房间迁移是另外的故障恢复问题，首版滚动更新不保证它们无损。

已有连接与监听套接字是不同资源：Go 的 TCPListener.Close 不关闭已接受的连接；systemd 的 socket activation 可保留待处理连接，但不会自动搬运本项目的内存房间与会话。因此不能只加一个 systemd socket 单元就宣称重启无损。参考 [Go net 文档](https://pkg.go.dev/net#TCPListener.Close)、[systemd.socket 官方说明](https://www.freedesktop.org/software/systemd/man/latest/systemd.socket.html)。

验收：隔离双节点连续对局中排空一服，验证原房间继续通信、补位与重连可用，新房进入另一服；留一个长局验证不会被超时踢出；演练错误程序、错误配置、启动失败、部署命令中断、回退及两服无余量。

## 统一管理页

复用现有状态页和采样，不引入数据库、Docker 或大型监控组件。先提供本机管理工具通过 SSH 汇总两服的浏览器页面；单服本机状态页仍可独立访问。节点不可达时显示最后采样时间和失联状态，不能以历史正常值代替当前状态。

页面显示：

- 每服实际运行版本、维护阶段、是否收新房、房间/玩家/连接数。
- 应用发送趋势、配置预算、队列与最近一分钟错误。
- 主机内存压力、进程内存、CPU、最近重启时间。
- 当前维护任务、剩余房间、等待原因、自检结果和回退记录。
- 当前容量风险解释，例如“发送预算接近上限”，而不是只给一个难理解的综合分数。

网页上的管理操作需接入与本机命令一致的权限校验和操作记录。首版先完成“看得见”与命令行维护，再接网页维护按钮；不以裸露公网管理接口换取方便。

## P3 与额外需要补齐的内容

| 内容 | 原因与范围 |
| --- | --- |
| 动态节点目录 | 安装支持此能力的客户端后，后续加服可读取更新的目录；采用有签名、修订号、有效期的配置，多个来源与本地内置/最近有效配置兜底。目录只做发现，故障不影响已有对局。现有旧客户端仍需更新一次才能获得该能力。 |
| 稳定节点标识 | 节点 ID 不复用；替换地址时为新节点分配新 ID，保留旧映射直到旧房间结束，避免完整码指向错误进程。 |
| 长局期间的新旧程序并行 | 等空房成为实际瓶颈后再设计房间感知入口与进程代次路由，使原房间加入、补位、重连仍进旧进程。仅分担监听或随机 TCP 转发不足以解决；需要独立专项验证，并限制两个进程共享的连接、内存和出口预算。 |
| 房间码复用保护 | 后续以房间代次或会话标识确认恢复目标，避免过期记录恰好命中同节点后来复用的四位码。保持旧版加入行为有明确兼容边界。 |
| 错误定位与慢连接保护 | 玩家看到可理解的失败原因与诊断编号；管理员可区分版本不匹配、维护、满额和超时。沿用现有基础限流，补握手及查询分类限制；考虑宿舍/校园等多人共用出口，避免一刀切封锁。 |
| 日志和磁盘额度 | 固定保留少量发布版本，限制日志大小与保留天数，记录配置/发布变化，避免小硬盘被日志或备份逐渐占满。 |
| 故障恢复 | 服务自动拉起只能恢复接收能力，不能恢复已丢失的内存房间。崩溃后的重建房间、关间恢复及跨服恢复另立方案，明确依赖客户端进度与会话检查点。 |
| 大厅体验 | 稳定性完成后推进房间自命名、版本筛选、搜索与刷新反馈；名称不代替房间码，也不增加中心游戏转发。 |
| 真实游玩验收 | 补 PC/Android 混合六人长局、无尽、关间补位、弱网和掉线重连；记录有代表性的负载与带宽，形成经测量的容量建议。 |

首版不为这些目标新增 Redis/MySQL 等常驻服务。两台小服务器的出口独立；增加节点主要扩大可承载的房间集合，单个大房间仍受所属节点的出口限制。

## 发布与验收约束

- 源码完成、测试通过、完整包生成、runtime 安装和公网部署分别记录状态，不用“已完成”概括未部署的功能。
- 任何破坏现有游戏协议或客户端理解的变化，都先列兼容矩阵，分别验证旧客户端/新服务、新客户端/旧服务及两端新版本。不将目录协议升级默认当成战斗协议不兼容。
- 首次部署先确认旧服权限、实际版本、备份与维护窗口；本计划不擅自重启正在承载玩家的服务。
- 涉及客户端时同步 PC/Android，交付可直接玩的完整包，保持存档与 Android 签名；通过检查后按用户要求保护当前进度、更新 runtime 并打开供检验。
- 第一批完成标准：带宽感知自动建房、服务端维护门禁、配置重载、趋势和兼容测试可用。第二批完成标准：完整双服滚动发布与失败回退演练通过，管理页能反映真实阶段。
