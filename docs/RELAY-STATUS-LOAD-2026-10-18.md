## 查看状态

```bash
cd /www/server/pvz-relay
./pvz-relay -status
watch -n 2 './pvz-relay -status'
./pvz-relay -status-json
```

`-status`显示中文信息后退出；watch每2秒查询，Ctrl+C只停止查看。状态HTTP默认`127.0.0.1:27778`，仅接受回环IP监听，未增加公网管理入口。`/`为每5秒刷新的页面，`/status`输出JSON，`/healthz`仅表示HTTP进程存活。HTTP连接有读写/空闲超时及头长度约束。原服务启动参数`-port 97`继续使用；`-admin ''`可禁用状态接口。

主要信息：在线连接/房外连接、玩家/房间数、公开待开局/已开局房间、掉线保留席；进程CPU（100%=占满一核）、Linux当前RSS、Go堆、整机可用内存、系统1分钟负载（JSON）；收发速率与累计值、转发/大厅查询、队列、容量拒绝、格式错误、控制频率超限、超时与写失败计数。

每秒缓存一次状态，网页请求不会逐次扫描和读取系统信息。读写路径只做原子计数；房间计数持锁期间不做网络或文件I/O。CPU按进程实际用户+内核CPU时间增量计算，RSS读取`/proc/self/statm`，不用Go保留空间冒充物理内存。无法获取的OS字段为null，首次CPU差分显示采样中。

连接/房间按秒汇总，事件发生后可能等约1秒显示；流量仅统计游戏TCP应用流，包含4字节帧头，不含IP/TCP头、ACK、重传及状态HTTP。转发计数表示成功入发送队列，发送帧计数表示实际整帧写完；异常断开可能产生差异。累计值重启归零，不保存日志历史、玩家名、房间码、IP或随机凭据。

浏览器可通过SSH本地转发查看，无需放行27778：在自己的电脑终端执行`ssh -N -L 127.0.0.1:27778:127.0.0.1:27778 root@服务器公网IP`，保持连接，再打开`http://127.0.0.1:27778/`。没有SSH转发时，直接在自己浏览器输入这个地址不会打开云服务器。

## 实测方法

实际运行最终同版Go逻辑的Linux amd64程序，通过真实TCP创建六人房。服务器绑到本机Ryzen 9 7945HX一个逻辑核心，`GOMAXPROCS=1`、`GOMEMLIMIT=192MiB`；客户端压测进程不绑该核。WSL2 Linux回环网络，无公网限速，Go正式非竞态构建。空载6秒，其余每档约10秒，加2秒预热；另做90秒持续观战与查询检查。

普通事件模型：每人每秒5个32字节载荷。密集事件模型：每人每秒20个64字节载荷。这里是已经指定单个目标的发出帧数；一条需要发给五位队友的广播在中继侧按五帧计算，不能只算一次。实际局内取决于漏怪、协作、伤害统计等事件频度；本测试不是游戏渲染或完整六人长局。

观战模型：每位玩家各发一路最大快照，120只僵尸＋60株植物，快照1087字节，分5片，每片6字节快照头＋4字节网络帧头，合计1137字节；当前节拍每8个100Hz更新约12.5次/秒。每路约0.114Mbps应用流。观战人数增加或同一场地被多人看时按观看连接数相加，植物/僵尸数量到快照上限后不会继续线性放大快照。

| 场景 | 单核CPU平均 | 峰值进程RSS | 发送应用流 |
|---|---:|---:|---:|
| 空载 | 0.08% | 6.8 MiB | 0.000 Mbps |
| 6人普通事件 | 0.32% | 7.1 MiB | 0.009 Mbps |
| 60人普通事件 | 2.10% | 7.9 MiB | 0.088 Mbps |
| 120人密集事件 | 9.40% | 11.9 MiB | 1.305 Mbps |
| 300人密集事件 | 20.15% | 13.2 MiB | 3.273 Mbps |
| 480人密集事件＋大厅10次/秒 | 29.45% | 16.2 MiB | 5.251 Mbps |
| 6人各看一路满编观战 | 1.02% | 9.1 MiB | 0.689 Mbps |
| 60人各看一路满编观战 | 8.12% | 11.8 MiB | 6.916 Mbps |
| 120人各看一路满编观战 | 14.78% | 12.4 MiB | 13.803 Mbps |
| 空大厅查询20次/秒 | 0.81% | 7.6 MiB | 0.002 Mbps |

上述短测普通事件和快照分片发送/接收计数一致，无队列满断开、容量拒绝、超时或写失败。另有60人各看一路＋每秒5次大厅查询持续91秒：CPU7.77%、峰值RSS11.8MiB、发送6.916Mbps，计数一致且无异常断开。这只是90秒持续检查，不代表几小时或弱网的稳定性保证。

额外验证512个真实房外连接到顶时第513个被关闭，管理查询仍可读；关闭后连接归零。128个真实房间到顶时第129房被拒，退房后房间和玩家归零。512连接和128房是保护上限，包含大厅短连接，不代表可承诺512人公网游戏。

## 对这台服务器的估计

- 当前中继把草坪、僵尸、伤害和增益计算留给客户端；普通地图变密不会使服务器承担游戏模拟。大厅是短查询，无数据库，本地最近记录完全不上传；它们的持续成本较低。
- 用户机器当前available约722MiB，比短测RSS约7～16MiB宽裕。初期可为中继、Go增长、套接字和日志预留64～128MiB观测预算；这不是硬内存上限或内核缓冲的保证。系统已有宝塔和其他任务，仍需看RSS、systemd服务内存和整机available；不把swap算成可长期依赖的游戏内存。
- 2核并不意味着能按本机Ryzen线性推算。共享/突发型云CPU、现有系统负载、网络往返与拥塞都未实测。普通几房至几十人可先上线观测，是否扩大以实际CPU、队列、断开和发送速率为准；不由短测直接承诺480人。
- 当前最大的可变项是观战。每路满编快照按0.15～0.20Mbps预留（含协议开销/波动），再留约30%带宽余量，得到下表。它是持续满编观战路数预算，普通联机、上传下载和宝塔流量仍需另扣。

| 公网出口带宽 | 满编观战初步预算 | 说明 |
|---|---:|---|
| 1Mbps | 约3～4路 | 一房六人同时观战可能接近带宽瓶颈 |
| 3Mbps | 约10～14路 | 还需扣除其他联机及站点流量 |
| 5Mbps | 约17～23路 | 超过后优先看带宽和队列，而非盲目加内存 |

阿里云购买的公网带宽主要对应服务器出方向；本程序的发送Mbps可作应用流参照，正式峰值以阿里云/系统网卡监控为准。依据：[阿里云公网带宽说明](https://www.alibabacloud.com/help/en/ecs/user-guide/network-bandwidth/)。没有开启观战时通常远低于该预算，但密集广播、补位补发和突发事件要另留空间。

实用观察：进程CPU持续接近可用核数×100%、整机available持续少于100MiB、队列反复增长或队列满计数持续上升时暂停扩容；发送应用流逼近购买带宽前就应留出协议及重传余量。累计一次异常不等于当前仍拥塞，要看计数是否继续增长。
