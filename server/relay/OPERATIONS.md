# 首批多服务器运维（2026-10-20）

本批服务器版本 `2026-10-20-operations1`，支持监测趋势、负载查询 v2、签名服务器清单和配置即时生效。程序换版、房间迁移与统一多服管理页属于下一批；本机状态页仍按节点查看。正式程序、双端完整包及 runtime 由“构建与发布”统一准备。源码完成不表示公网已更新。

## 首次安装

首次换成这个程序仍会丢失旧进程内存中的房间，须逐服安排无玩家的维护窗口。不能直接覆盖正在运行的程序并称为热更新。旧服对新开局载荷 45 字节可以原样转发；为该字段本身无需先更服。动态清单、新负载指标和配置重载则需要部署本批服务器。

沿用现有游戏端口和服务用户，在服务启动参数末尾加绝对配置路径，例如：

```bash
/www/server/pvz-relay/pvz-relay -port 97 -admin 127.0.0.1:27778 -config /www/server/pvz-relay/operations.json
```

不开放 27778 公网端口。配置、目录和程序须可被服务用户读取；签名私钥不上传游戏服务器。以下是 **3 Mbps 节点示例**，其他节点按实际带宽填写；不知道时填 0，不推断为 3 Mbps。

```json
{
  "revision": 1,
  "bandwidth_mbps": 3,
  "send_budget_mbps": 2.25,
  "weight": 100,
  "accept_new_rooms": true,
  "busy_cpu_percent": 85,
  "catalog_path": "relay-nodes.bin"
}
```

`catalog_path` 相对配置文件目录解析。签名公钥默认已固定在服务端和双端客户端，不需填入普通配置。公网带宽不是测量结果；2.25 Mbps 是预留协议开销与其他服务余量的初始应用预算，应结合云监控校准。`send_budget_mbps=0` 且带宽已知时自动采用带宽的 75%；两者均为 0 表示未知，不显示精确剩余容量。

## 即时修改

1. 复制配置为同目录的临时文件，修改所需值并增加 `revision`。
2. 用完整 JSON 保存，再在同一文件系统中重命名替换原文件，避免编辑到一半被读取。
3. 等约 1–2 秒，查看 `./pvz-relay -status-json` 的 `operations.config_revision` 和 `config_error`。修订必须与预期一致，错误栏为空。

```bash
cp -- /www/server/pvz-relay/operations.json /www/server/pvz-relay/operations.next.json
# 编辑 operations.next.json；例如把 revision 从 1 改为 2。
mv -- /www/server/pvz-relay/operations.next.json /www/server/pvz-relay/operations.json
cd /www/server/pvz-relay
./pvz-relay -status-json
```

无需重启服务。`accept_new_rooms=false` 只停止新建房，已有房间转发、加入和凭据重连继续工作；恢复时增加修订并改为 true。重载与建房在同一个房间锁下排序，重载完成后不会再受理旧开关允许的新建房。

错误、超长、未知字段、旧修订或同修订不同内容都保留原配置，并在状态页说明。启动时配置无效则拒绝启动，避免以错误预算或清单运行。可热调范围为预算、节点权重、CPU 软阈值和停接新房；256 房、512 连接、每房 6 人仍是固定保护上限，查询也占连接。

## 发布服务器清单

客户端从已知节点获取签名清单，并保存验证通过的缓存。以后增加服务器：安装中继、开放游戏端口、更新清单、签名，把同一份签名文件发布到现有可达节点。支持本功能的客户端在下一次有效创建/大厅刷新时发现新节点，无需重新下载。旧客户端仍只认识它内置的节点。

清单 JSON 示例：

```json
{
  "revision": 1,
  "expires_at": "2027-10-20T00:00:00Z",
  "nodes": [
    {"id":"1","host":"101.200.131.182","port":97,"weight":100,"create":true,"directory":true},
    {"id":"2","host":"101.201.226.1","port":97,"weight":100,"create":true,"directory":true}
  ]
}
```

ID 为 1–65535 的十进制数字，最多 64 条记录，签名文件最多 8192 字节。地址支持 IPv4/DNS。新增机器使用新 ID；已发布 ID 的地址/端口不能更改、ID 不能删除或复用。退役节点保留原地址并把 `create`、`directory` 改为 false，原完整码仍指向原节点。若 DNS 指向变化，也必须保证原房间地址生命周期，不用改解析代替房间迁移。

在可信维护电脑上构建维护工具。签名私钥只用于维护工具，公钥已在本批双端固定；发布以后不要重新生成身份。首次签名不带 `-previous`，后续签名必须指定上次正式清单校验修订与身份连续性：

```bash
go build -o relay-catalog ./cmd/relay-catalog
./relay-catalog sign -private /安全位置/catalog-private.key -input relay-nodes.json -output relay-nodes.next.bin -previous relay-nodes.bin
./relay-catalog verify -public /安全位置/catalog-public.key -input relay-nodes.next.bin
```

本机 Windows 使用生成的 `.exe` 和 Windows 路径。向所有节点上传已签名的 `relay-nodes.next.bin`，在配置指定目录内重命名成 `relay-nodes.bin`。清单自身修订增加即可，若普通配置未变无需增加其修订。服务器约一秒内验证并应用；检查状态页目录修订、节点数量、有效期与错误栏，随后用完整码和大厅验收新增节点。

定期在到期前增加目录修订、延长有效期并签名发布。过期远端清单不会被新采用；已验证的本地旧缓存只保留已知路由，连接仍需实际可达。错误签名、旧修订、截断、冲突 ID 不会替换有效目录。节点全部离线时仍不能凭清单恢复服务。私钥丢失后无法继续向已发布客户端签发新目录，必须独立备份并限制访问；私钥泄露需要客户端更新信任锚。

## 分流与兼容

- 新建房参考房间/连接占用、应用发送预算、CPU、低可用内存、队列和最近一分钟错误；负载接近时随机分散。清单权重与节点实时权重共同调整优先级。
- 所有节点繁忙但未硬满时仍尝试负载较低的一台；繁忙是建议，不能因此自动停接新房。明确维护、硬满和过期的详细样本会被排除。
- 每批最多 4 个查询连接。清单查询总限时约 1.8 秒、普通自动刷新冷却 30 秒；容量探测总限时 5 秒，有可用结果后给其他节点约 400 毫秒补充窗口。大厅单页查询最多 5 秒，失败节点标为部分失败并保留成功节点条目。大目录中一页可能不能覆盖全部离线节点；后续刷新轮换首批节点。
- 初次建房只有连接前失败、尚未尝试发请求或明确 `SERVER_BUSY` 拒绝才跨节点重试。已发创建请求但结果不明时停止重试；返回可取消未完成创建。收到欢迎后不迁移房间，加入/重连固定原节点。
- 旧容量 v1 保持 16 字节；新容量 v2 为 44 字节。新端按 v2→v1→旧大厅查询回退，未知负载采用保守分数，不认为是零。大厅原 v1/v2 与旧加入方式保持不变。
- 动态完整码最大 10 字符，例如 `10-ABCD`。4 字符旧码仍固定原始节点 1，不会跨服搜索同码。大厅保留每条房间的准确目标，退役开关不改旧码归属。
- 游戏开局 44/45 字节都由中继逐字节转发，不解析或剥离新增规则；新旧客户端开局格式不同，下一批须统一客户端兼容版本，不能在同房混用。

## 查看状态与实际边界

服务器本机访问 `http://127.0.0.1:27778/`。远程电脑沿用 SSH 本地转发，把本地端口转到该服务器的 127.0.0.1:27778，再用浏览器访问本地端口。多服用不同本地端口分别查看，不需要数据库或 Docker。

每秒采样、每 5 秒保留一条，固定最多 120 条（约 10 分钟），无需打开网页才开始记录。`/status` 返回当前 JSON，`/history` 返回趋势，`/healthz` 只代表管理 HTTP 存活。网页新增配置修订/错误、清单修订/数量/过期提示、停接状态、应用预算与最近一分钟异常；CPU 100% 为一核，累计计数重启清零。

单节点 256 房、512 连接不等于可流畅承载这么多人。3 Mbps 的实战瓶颈主要取决于每房事件量、重传及其他流量。增加服务器只增加可选容量，不会自动搬走旧房；程序重启、机器故障会丢失内存房间。新增监测为有界内存和单采样循环，未承诺阿里云上的最终人数，需要上线后按真实趋势校准。
